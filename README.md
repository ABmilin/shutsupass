# ShutsuPass — セットアップ手順（ステップ1: 動作確認）

このステップでは、フロントエンド・バックエンド・DBの3コンテナが立ち上がり、
お互いに通信できることを確認します。認証や証明書申請の機能はまだ実装されていません。

## 手順

1. このフォルダをプロジェクトフォルダ（例: `CLD5F`）に展開する
2. `.env.example` をコピーして `.env` を作成する

   ```
   cp .env.example .env
   ```

3. Docker Desktopを起動しておく
4. プロジェクトルートで以下を実行する

   ```
   docker compose up --build
   ```

5. 起動が完了したら、ブラウザで以下にアクセスする

   ```
   http://localhost:5173
   ```

6. 画面に以下がすべて「✅」で表示されていれば成功です

   - Frontend: 起動中 ✅
   - Backend: 接続OK ✅
   - Database: 接続OK ✅ (ShutsuPass DB initialized)

## 止め方

```
docker compose down
```

DBのデータごと消したい場合（初期化しなおしたい場合）は以下を使う:

```
docker compose down -v
```

## うまくいかない場合

- `docker compose ps` で3つのコンテナ（db, backend, frontend）が起動しているか確認
- `docker compose logs backend` / `docker compose logs db` でエラーログを確認
- ポート5432・4000・5173がMac上の他のプロセスで使われていないか確認

## ステップ2: 認証機能（学生・職員ログイン）

`users`テーブルを追加したため、**既存のDBボリュームを一度削除してから**起動し直す必要があります（初期化スクリプトはボリューム作成時にしか実行されないため）。

```
docker compose down -v
docker compose up --build
```

起動後、`http://localhost:5173` にアクセスすると、ログイン画面が表示されます。

### 試し方

1. 「アカウントがない場合はこちら」から登録画面へ
2. 区分（学生／職員）を選び、ID・氏名・パスワード（8文字以上）を入力して登録
3. 自動的にログインされ、それぞれのダッシュボード（仮画面）に遷移します
4. 一度ログアウトし、今作ったIDでログイン画面から再ログインできることも確認してください

### 実装内容

- `users`テーブル（role, login_id, password_hash, display_name）
- バックエンド: `POST /api/auth/register`, `POST /api/auth/login`（bcryptでハッシュ化、JWT発行）
- バックエンド: `GET /api/me`（JWT検証のミドルウェア動作確認用、要認証）
- フロントエンド: ログイン画面（学生/職員タブ切り替え）、登録画面、ダッシュボード（仮画面）、ログイン状態のrole別アクセス制御

## ステップ3: 証明書の申請機能（学生側）

`document_types`・`applications`テーブルを追加したため、再度ボリュームを削除してから起動してください。

```
docker compose down -v
docker compose up --build
```

### 試し方

1. 学生アカウントでログイン
2. ダッシュボードの「証明書を新規申請」から申請フォームへ
3. 証明書の種類を選ぶと、その種類に応じた入力項目（学部・学科、提出先など）が表示される
4. 部数・受け取り方法を選んで「申請する」
5. 「お支払い金額」と「窓口でお支払いください」という案内が表示される
6. ダッシュボードに戻ると、今の申請が一覧に「申請中（支払い待ち）」として表示される

### 実装内容

- `document_types`テーブル: 証明書の種類ごとに手数料・必要項目(JSON)をマスタ管理（在学証明書・成績証明書・卒業見込証明書を初期データとして投入）
- `applications`テーブル: 学生の申請データ、ステータス管理（submitted → payment_confirmed → issued → completed / rejected）
- バックエンド: `GET /api/document-types`、`POST /api/applications`（申請作成、必須項目チェック、手数料自動計算）、`GET /api/applications/mine`
- フロントエンド: 証明書の種類に応じて入力項目が動的に切り替わる申請フォーム、申請完了画面（手数料・窓口案内表示）、ダッシュボードでの申請一覧・ステータス表示

## ステップ4: 職員側の画面（申請の処理）

今回はテーブル構造の変更はないので、`down -v`は不要です。通常の再起動で反映されます。

```
docker compose up --build
```

### 試し方

1. 職員アカウントでログイン（前回作ったものが残っていればそのまま、なければ職員として新規登録）
2. さきほど学生として作った申請が一覧に表示されているか確認
3. 学籍番号または氏名で検索できることを確認
4. 申請の「支払い確認」ボタンを押す → ステータスが「支払い確認済み」に変わる
5. 「発行済みにする」ボタンを押す → ステータスが「発行済み」に変わる
6. 窓口受取の申請であれば「受け渡し完了」ボタンが表示され、押すと「受け取り完了」になる
7. 別の申請で「却下」ボタンを押すと、理由の入力を求められ、入力すると「却下」ステータスになる
8. 学生アカウント側でも再ログインし、ダッシュボードのステータス表示が更新されていることを確認

### 実装内容

- バックエンド: `GET /api/applications`（職員向け、検索・ステータス絞り込み対応）、`PATCH /api/applications/:id/status`（支払い確認／発行／受け渡し完了／却下。不正なステータス遷移はエラーになるよう制御）
- フロントエンド: 職員ダッシュボード（検索・フィルタ、申請ごとの操作ボタン、経過日数表示）

## ステップ5: 証明書PDF生成 + デザイン刷新

`applications`テーブルにカラムを追加した（`pdf_path`, `issued_at`）ため、再度ボリュームを削除してください。また、バックエンドのDockerfileを変更した（Chromium・日本語フォントを追加）ため、ビルドに少し時間がかかります。

```
docker compose down -v
docker compose up --build
```

初回ビルド時、Chromiumのインストールで数分かかることがあります。気長にお待ちください。

### 試し方

1. 職員アカウントでログインし、支払い確認まで進んだ申請の「発行済みにする」を押す
   - この時、裏側でテンプレート（HTML）+配置情報（JSON）+申請データからPDFが自動生成されます
2. 「PDFを確認」ボタンが表示されるので、押してPDFが正しく表示されるか確認（学部・学籍番号・氏名などが証明書の枠内に収まっているか）
3. 学生アカウント側でログインし直し、受け取り方法が「ダウンロード」の申請であれば「PDFをダウンロード」ボタンが表示されることを確認
4. 窓口受取の申請は、職員側で「受け渡し完了」まで進めると学生側もステータスが更新される

### 実装内容

- `backend/templates/`: 証明書ごとのHTMLテンプレート（枠）と`.layout.json`（mm単位の配置情報）を分離管理。証明書の様式変更はJSONの数値変更のみ、新しい証明書の追加はテンプレート1組の追加のみで対応可能
- `backend/src/pdf/generate.ts`: テンプレート+配置情報+申請データを合成し、Puppeteer(Chromium)でPDFを生成
- バックエンドDockerfileをChromium・日本語フォント対応に変更（`node:20-slim` + `chromium` + `fonts-noto-cjk`）
- `PATCH /api/applications/:id/status`の`issue`アクション実行時にPDFを自動生成
- `GET /api/applications/:id/pdf`: 申請者本人（ダウンロード期限1週間以内）または職員のみアクセス可能なダウンロードエンドポイント
- デザイン刷新: 紺色×朱色（印鑑をイメージ）のデザインシステムを`index.css`に整理し、全画面に適用。申請の進捗を視覚的に示すステッパー表示を追加

## ステップ6: パスワードを忘れた場合の対応

`users`テーブルにカラムを追加した（`security_question`, `security_answer_hash`）ため、再度ボリュームを削除してください。

```
docker compose down -v
docker compose up --build
```

### 試し方

**職員の新規登録**
1. 職員として新規登録する際、秘密の質問と答えの入力が必須になっていることを確認

**職員のパスワードを忘れた場合**
1. ログイン画面の「パスワードをお忘れの場合」→ 職員タブ
2. ユーザー名を入力すると、登録した秘密の質問が表示される
3. 答えと新しいパスワードを入力すると再設定される
4. 新しいパスワードでログインできることを確認

**学生のパスワードを忘れた場合(窓口対応)**
1. 職員でログインし、ダッシュボードの「学生のパスワードをリセット」
2. 学籍番号または氏名で学生を検索
3. 「パスワードをリセット」を押す（確認ダイアログが出ます）
4. 一時パスワードが画面に表示される
5. 学生アカウント側で、その一時パスワードでログインできることを確認

**パスワード変更(共通)**
1. ログイン中、ヘッダーの「パスワード変更」から、現在のパスワードを入力して新しいパスワードに変更できることを確認

### 実装内容

- `users`テーブルに`security_question`, `security_answer_hash`を追加（職員のみ設定、bcryptでハッシュ化）
- バックエンド: `POST /api/auth/forgot-password/question`, `POST /api/auth/forgot-password/reset`（職員向け）、`PATCH /api/auth/change-password`（共通）
- バックエンド: `GET /api/users/students`（学生検索）、`POST /api/users/:id/reset-password`（一時パスワード発行、職員のみ）
- フロントエンド: パスワードを忘れた場合の画面（学生/職員タブ）、パスワード変更画面、職員向け学生パスワードリセット画面

## ステップ10: PDF生成の廃止・厳封の選択式化・提出先の削除

**重要な設計変更**です。「証明書そのものを電子的に生成する」のはやめ、システムは**申請〜支払い〜発行までの進捗管理**に専念する形にしました。実際の証明書は、大学の既存の方法で作成します。これに伴い、Dockerの構成もシンプルになりました（Chromium・日本語フォントのインストールが不要に）。

`document_types`・`applications`テーブルを変更し、Dockerfileも変更したため、イメージを作り直してください。

```
docker compose down -v
docker compose up --build
```

(前回よりビルドが速くなっているはずです。Chromiumのインストールがなくなったため)

### 試し方

1. 学生の新規申請画面で、各証明書の項目から「提出先」がなくなっていることを確認
2. 「使用目的」（就職活動／その他）に加えて、**「厳封での受け渡しを希望する」チェックボックス**が独立して選べることを確認（就職活動を選ばなくてもチェックできる）
3. チェックを入れて申請すると、職員側の一覧に「⚠️ 厳封が必要です」と表示されることを確認
4. 職員が「発行済みにする」を押しても、PDFは生成されず、ステータスが「発行済み」に変わるだけであることを確認（学生側にも通知が届く）
5. 職員画面から「PDFを確認」ボタンがなくなっていることを確認

### 実装内容

- 証明書PDFの生成機能（Puppeteer・テンプレート・配置情報・自動削除）をすべて削除
- バックエンドのDockerfileをシンプルな`node:20-alpine`構成に戻す(Chromiumのインストール不要に)
- `document_types`の各書類から「提出先」項目を削除（使用目的と役割が重複するため）
- `applications`に`needs_sealing`（厳封希望、独立したチェックボックス）を追加。「使用目的」から自動判定するのではなく、学生が明示的に選択する方式に変更
- 職員画面の厳封バッジは`needs_sealing`を直接参照するよう変更

今後、`down -v`が必要になった場合でも、毎回アカウントを作り直さなくていいように、最初から動作確認用のアカウントが入るようにしました。

### DBの中身を確認する方法

**ターミナルから直接見る場合:**

```bash
docker exec -it shutsupass-db psql -U shutsupass -d shutsupass -c "SELECT id, role, login_id, display_name FROM users;"
```

対話的に操作したい場合は、以下で入って`\dt`（テーブル一覧）や`SELECT * FROM applications;`のようなクエリを実行できます。

```bash
docker exec -it shutsupass-db psql -U shutsupass -d shutsupass
```

**GUIツールから見る場合:**

DBのポート(5432)はMac側に公開されているので、VSCodeの拡張機能（PostgreSQL、SQLToolsなど）や、TablePlus・PosticoなどのDBビューアアプリから、以下の情報で接続できます。

| 項目 | 値 |
|---|---|
| Host | localhost |
| Port | 5432 |
| User | shutsupass |
| Password | shutsupass |
| Database | shutsupass |

### 補足: 今後アカウントが消える条件

通常の`docker compose up`/`down`（`-v`なし）ではデータは残ります。データが消えるのは`down -v`を実行した時（DBのボリューム自体を削除する操作）だけです。今回で主要なテーブル変更は一段落したので、今後はこの操作の頻度は減るはずです。

- 認証、証明書申請、支払い承認フロー、通知、パスワードリセットなど、要件定義書の主要機能が一通り動作

2. **料金・ビジネスプランの検討**: 「実装後に職員へ再ヒアリングしてから決める」という方針で保留にしていた部分です。実装が一区切りついたので、具体化を進めるタイミングです

4. **最終動作確認(通しテスト)**: 学生登録→申請→支払い確認→発行→受け渡し、却下→再申請、パスワードリセット(学生・職員両方)を、一通り通しで確認しておくと安心です

4. 学生ダッシュボードで、まとめて申請した2件が枠で囲まれ、「🔗 まとめて申請した2件」として表示されることを確認
5. 職員ダッシュボードでも同様にまとめて表示され、両方とも「申請中」ステータスなら「2件まとめて支払い確認」ボタンが出ることを確認
6. 「2件まとめて支払い確認」を押すと、2件とも一括で支払い確認済みになることを確認
7. 「支払い確認済み」まで進めると「2件まとめて発行」ボタンが出て、押すと発行前確認ダイアログに2件とも表示され、チェック後にまとめて発行できることを確認

### 実装内容

- `applications.group_id`（UUID）を追加。「続けて申請」で出された複数の申請は、同じグループIDで束ねられる
- バックエンド: 申請作成時にグループIDを発行・引き継ぎ、グループの合計金額を返す。`PATCH /api/applications/group/:groupId/status`でグループ単位の一括ステータス更新（却下は個別対応のため対象外）
- フロントエンド: 学生・職員どちらの画面でも、同じグループの申請を枠で囲んでまとめて表示。職員側は、グループ内が全て同じステータスの場合のみ一括操作ボタンを表示
- 発行前確認ダイアログを、単体・グループ両対応に汎用化

### 対応できる範囲

「成績証明書2通・厳封あり」→「卒業見込証明書1通・厳封なし」のように、**異なる種類・異なる厳封条件の組み合わせ**を、同じ来庁機会の申請としてまとめて扱えます。データ構造（1申請＝1種類・1条件）自体は変更せず、グループ化という形で対応しているため、既存の申請フロー・承認フローへの影響を抑えています。

## ステップ26: 申請フォームをカート形式に変更

テーブル構造の変更はないので、`down -v`は不要です（既存の`group_id`列をそのまま使います）。

```
docker compose up --build
```

### 変更点

これまでの「1件申請→続けて申請→後からグループとして束ねる」という流れから、**「複数件をカートに入れてから、まとめて1回で申請する」**という流れに変更しました。

### 試し方

1. 証明書の種類・部数・厳封などを入力し、「＋ カートに追加する」を押す（この時点ではまだ申請されない）
2. フォームがリセットされるので、続けて違う種類の証明書を入力し、再度「カートに追加する」
3. 画面上部に「🛒 カート（2件）」が表示され、それぞれの内容と合計金額が確認できることを確認
4. カート内の項目を「削除」で取り消せることを確認
5. 「この内容でまとめて申請する」を押すと、2件まとめて送信され、合計金額の完了画面が表示されることを確認

### 実装内容

バックエンド側は変更していません。以前実装した「グループID」の仕組み（1件目のレスポンスで払い出されたIDを、2件目以降のリクエストで引き継ぐ）をそのまま活用し、**フロントエンドが複数件を順番に送信するだけ**という形にしました。これにより、リスクを抑えつつ「カートで組み立ててから一括送信する」という体験を実現しています。

ヒアリングにあった「5通を2・2・1でまとめて、そのうち1つは厳封」のような細かい組み合わせにも、この形で対応できます。

## ステップ27: 厳封の「まとめ方」を指定できるように

`applications`テーブルに`seal_group_label`列を追加したため、再度ボリュームを削除してください。

```
docker compose down -v
docker compose up --build
```

### 試し方

1. カートに追加する際、「厳封を希望する」にチェックを入れると「まとめ方の目印（任意）」欄が出ることを確認
2. 種類の違う証明書2つに、同じ目印（例: 「A社提出用」）を入力してそれぞれカートに追加
3. カート内の表示に「厳封（A社提出用）」と出ることを確認
4. まとめて申請 → 学生・職員どちらの画面でも、同じ目印がラベルとして表示されることを確認

### 実装内容

「AとBをセットで1つの封筒にまとめたい」という、証明書の種類をまたいだ厳封のグルーピング指定に対応しました。複雑な「複数選択してまとめる」操作画面ではなく、**任意の目印（自由記述のラベル）を、まとめたい証明書に同じ文言で入力してもらう**、というシンプルな方式にしています。同じラベルが付いた証明書は、職員が同じ封筒にまとめて対応する、という運用です。

これはヒアリング原文にあった「まとめる・別々にする指定」という要望への対応で、以前の実装（厳封の有無のみを持たせる設計）では拾いきれていなかった部分でした。

## ステップ28: 部数の内訳を分けて厳封を指定できるように

テーブル・APIの変更はないので、`down -v`は不要です（フロントエンドのみの変更です）。

```
docker compose up --build
```

### 何が変わったか

これまでは「部数」が証明書の種類ごとに1つの数字で、厳封の有無・目印も1種類の証明書につき1パターンしか指定できませんでした。そのため、「卒業見込証明書2部のうち1部だけ厳封」のような指定をするには、学生が同じ証明書を部数1で2回に分けて選び直す必要がありました。

これを、**1つの証明書を設定する画面の中で「内訳」を追加できる**形に変更しました。

### 試し方

1. 証明書の種類を選ぶと、「部数・厳封の内訳」という欄が表示される
2. デフォルトで内訳が1行あるので、部数を1にして厳封にチェックを入れ、目印（例: A）を入力
3. 「＋ 内訳を追加」で2行目を追加し、部数1・厳封なしのまま
4. 「カートに追加する」を押すと、**カートに2件（それぞれ1部ずつ、片方だけ厳封A）**として追加されることを確認
5. 内訳を追加しなければ、これまで通り1件として追加される（挙動は変わらない）

### 実装の考え方

バックエンドやAPIの形は変更していません。「カートに追加する」ボタンを押した時に、内訳の行数だけ`CartItem`を自動生成してカートに積む、というフロントエンドだけの変更です。学生からすると、同じ証明書を何度も選び直す必要がなく、1回の操作の中で部数の割り振りが完結します。

## ステップ29: 帳票レイアウト編集・印刷プレビュー機能

`document_types`テーブルに`layout`列を追加したため、再度ボリュームを削除してください。

```
docker compose down -v
docker compose up --build
```

### 何を作ったか

「学生の入力データから、そのまま書類が出来上がる」体験を、**Docker側に手を加えず**（Puppeteer・Chromiumは使わない）実現しました。

- 職員が「申請書の種類を管理」→「帳票レイアウトを編集」から、各項目（学籍番号・氏名・学部学科など）を**クリックで好きな場所に配置**できる
- 配置情報はデータベースに保存され、証明書の種類ごとに使い回される
- 職員ダッシュボードの各申請カードから「帳票プレビュー」を開くと、その申請の実データが配置通りに表示される
- ブラウザ標準の「印刷する」機能（Ctrl+P）でPDFとして保存できる

### 試し方

1. 「申請書の種類を管理」→ 在学証明書などの「帳票レイアウトを編集」を開く
2. 「学籍番号」の「配置する」を押し、枠内の好きな場所をクリック→配置されることを確認
3. 同様に「氏名」「学部・学科」なども配置し、「レイアウトを保存」
4. 職員ダッシュボードで、その証明書の申請の「帳票プレビュー」を開く
5. 配置した通りの位置に、実際の申請データ（学籍番号・氏名・学部学科など）が表示されることを確認
6. 「印刷する」→ ブラウザの印刷ダイアログで「PDFとして保存」を選ぶと、PDFが作成できることを確認
7. プレビュー画面の下部に「本画面はシステムによる自動生成の参考表示であり、大学の公式な証明書ではありません」という注記が表示されていることを確認

### 設計上の判断

- **PDF生成ライブラリ（Puppeteer）を使わず、ブラウザの印刷機能に任せる方式**にした。これにより、Docker環境にChromiumを追加する必要がなく、以前削除して軽量化した構成を維持できている
- 配置方法は、数値でのmm指定ではなく、**画面をクリックして位置を決める**簡易的な方式にした。本格的なドラッグ&ドロップ編集ほどの作り込みはしていないが、数値入力よりは直感的に扱える
- 生成される帳票には、「大学の公式な証明書ではない」という注記を必ず表示する。これは、要件定義書でこれまで一貫して述べてきた「証明書PDFの自動生成は行わない」という設計判断と矛盾しないようにするための、意図的な配慮である

### 正直な限界

- 新しい種類の証明書を追加する際、罫線や全体のデザインといった「枠」自体は、今のところ固定のフォーマットになっている。職員が自由に変更できるのは、あくまで各項目の配置場所のみ
- 学生自身が自分の申請の帳票プレビューを見るための導線は、今回は追加していない（職員側のみ）
